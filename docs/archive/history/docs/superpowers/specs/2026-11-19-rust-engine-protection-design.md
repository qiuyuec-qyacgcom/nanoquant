# Rust 引擎保护单控制面设计

## 意图与边界
为 Rust 引擎补齐 Binance Algo 保护单查询和单笔撤销接口，供现有控制面查看、维护交易所侧保护单。查询实时读取交易所，不新增本地缓存；撤销仅接受有效 algo ID，并在发送 DELETE 前 fresh 查询确认该 ID 仍属于当前保护单。非目标是批量撤销、报价 enrichment 和其他订单接口改造。

## 实现方案
方案一：把保护单路由接入 `AppState`，复用 `EngineControl` 的加密凭证、签名构造与数据库限频冷却；推荐此方案，可保持运行时和 HTTP 控制面使用相同的凭证来源及冷却记录。方案二：在路由独立实现 Binance 客户端，会重复签名和密钥处理并可能绕过冷却，不采用。方案三：将路由迁入后台运行时任务，会扩大生命周期和消息传递改动，不采用。

## 行为
`GET /engine/protection` 返回 `items/count/mode`，每项采用 Python 对应接口的字段。Binance `-1003` 返回空列表并标注 `degraded`，持久化限频截止时间；其他交易所失败返回 503。`DELETE /engine/protection/{algo_id}` fresh 查询后只撤销仍存在的保护单，不存在返回 404；交易所明确拒绝撤销返回 400。所有请求使用当前交易环境签名凭证。

## 约束与验证
不增加依赖；不触碰无关工作区改动。测试应覆盖请求路由状态类型、保护单行转换、未知 ID 不撤销及限频降级/持久化。运行 Rust 完整测试套件。
